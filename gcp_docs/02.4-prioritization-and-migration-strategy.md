# Prioritization and migration strategy

A key element of migration planning is to establish prioritization criteria. The point of this exercise is to understand the order in which applications will be migrated. The strategy is to take an iterative and progressive approach to evolve the prioritization model.

## Prioritizing applications

This stage of assessment focuses on establishing initial criteria to prioritize low-risk and low-complexity workloads. These workloads are good candidates for pilot applications. Using low-risk, low-complexity workloads in initial migrations reduces the risk and gives teams the opportunity to gain experience. These criteria will be evolved in further assessment stages to align prioritization with business drivers when creating the migration wave plan.

The initial criteria should prioritize applications with a small number of dependencies, running in cloud-supported infrastructure, and from non-production environments. An example would be applications with 0–3 dependencies ready to rehost as-is in a development or test environment. These criteria are valid for defining the pilot applications and potentially the first and second migration waves, depending on the level of cloud adoption maturity and confidence levels.

### Deciding what initial criteria to use

Select 2–10 data points to use for prioritizing your first workloads. These data points come from your initial data collection (refer to the [data collection](./02.3-initiating-data-collection.md) section).

Next, define a score, or weight, for each possible value of each data point. For example, if the environment attribute is selected, and the possible values are production, development, and test, each value is assigned a score, a greater number representing higher priority. Although it is optional, we recommend assigning a multiplying factor for importance or relevance to each data point. This optional step provides a higher-level differentiator to emphasize what is more important, which helps to keep the criteria aligned as you iterate on assigning scores to the values.

Based on the strategy to prioritize low-risk, simple applications for the first few migration waves, the following table shows example attributes selection and their value assignments.

| Attribute (data point) | Possible values | Score (0-99) | Importance or relevance multiplying factor |
| --- | --- | --- | --- |
| Environment | Test | 80 | High (1x) |
| Environment | Development | 50 | High (1x) |
| Environment | Production | 20 | High (1x) |
| Business criticality | Low | 60 | High (1x) |
| Business criticality | Medium | 40 | High (1x) |
| Business criticality | High | 20 | High (1x) |
| Regulatory or compliance framework | None | 60 | High (1x) |
| Regulatory or compliance framework | FedRAMP | 10 | High (1x) |

| Operating system support | Unsupported in cloud | 10 | Medium-high (0.8x) |
| Number of compute instances | 1-3 | 60 | Medium-high (0.8x) |

Make sure that you select attributes that can act as key differentiators between applications. Otherwise, the criteria will result in many workloads sharing the same priority. After you apply the model, we recommend looking at the top and bottom of the resulting ranking to see if you agree. If you don't generally agree, you can revisit the criteria that you used to score the workloads.

After you obtain a ranking, look at the distribution of scores across the entire portfolio. The scores themselves do not matter. It is the difference between scores that matters. For example, you might find that the top total score is 8,000 and the bottom score is 800. Consider plotting the resulting scores as a histogram, so you can verify that you have a good distribution. The ideal distribution looks like a standard bell curve, with a few very high-priority workloads and a few very low-priority workloads. The majority of applications will be somewhere in the middle.

Another key aspect of initial prioritization is to include internal teams or business units that show interest in being early adopters of the cloud. These could be a considerable lever in obtaining business support to migrate a given application, especially in the early days. If this is the case in your organization, include the business unit attribute in the preceding table. Assign a high score to those business units that are willing to come forward with their applications. Using the business unit attribute will help bring those applications to the top of the list.

After you agree with the resulting ranking, select the top 5–10 applications. These will be your initial application migration candidates. Refine the list so that you confirm 3–5 applications. This helps you to take a targeted approach when performing a detailed application assessment. For more information, see [Prioritized applications assessment](./03-prioritized-applications-assessment.md).

## Determining the R type for migration and modernization

Deciding on a disposition and migration strategy for each application and associated infrastructure has direct implications for migration speed, cost, and level of business benefit. It is critical to determine strategy based on a balanced combination of factors, including business drivers, technical guiding principles, prioritization criteria, and business strategy.

Sometimes these factors create conflicting views. For example, the primary driver might be innovation and agility, while at the same time you need to reduce costs quickly. Modernizing all applications in scope will reduce costs in the long run, but requires a greater investment upfront. In that case, one approach is to migrate non-differentiating applications using strategies that require less effort, such as **rehost** (to **Google Compute Engine**) or **relocate** (to **Google Cloud VMware Engine**), or **replatform** (to **Cloud SQL / AlloyDB** or **GKE / Cloud Run**). That provides quick operational efficiencies and cost reduction in the short term, allowing you to reinvest savings into modernizing strategic applications.

However, starting with a blanket lift-and-shift of every application—without first checking whether an application should be kept as-is, consolidated, or retired—can waste budget on low-value workloads and delay modernization benefits. To prevent this, we recommend a **two-stage decision approach**:

### Stage 1: Strategic Disposition Pre-Filter (Gartner TIME + Redundancy Check)

Before funneling an application into a cloud migration path, evaluate its strategic disposition across **Business Value / Functional Fit** and **Technical Quality / Operational Health**, plus functional overlap across the portfolio:

- **Eliminate (Retire or Consolidate):** *Low Business Value + Low Technical Health (or >70% functional overlap with another existing application).* Decommission the workload (**Retire**) or consolidate its users into an existing platform rather than migrating it.
- **Tolerate (Retain & Optimize in Place):** *Low/Medium Business Differentiation + High Technical Health (stable, compliant, low run cost, and no hard data-center exit deadline).* Keep running in the current environment (**Retain**) and optimize licensing/resources in place.
- **Migrate (Fix Technical Debt / Exit Infrastructure Constraints):** *High Business Value + Low Technical Health (or subject to a hard data-center exit / hardware EOL deadline).* Proceed to **Stage 2 (the 6 Rs / 7 Rs Decision Tree)** to select the optimal migration or replacement path.
- **Invest (Modernize & Scale):** *High Business Value + High Technical Health (strategic differentiator).* Proceed to **Stage 2** to evaluate cloud-native refactoring (**Cloud Run**, **GKE**, **AlloyDB**, **BigQuery/Vertex AI**) or managed replatforming.

### Stage 2: How to determine a 6 Rs (or 7 Rs) strategy for your applications

At this stage of assessment, incorporate the decision tree model to guide technical strategy selection for each in-scope workload (see the complete [6 Rs Decision Tree Guide & Worked Examples](./6rs-decision-tree.md)). In the tree, the most complex approaches, such as **refactor / re-architect**, are reserved for strategic workloads with high functional change rates and available investment. Note that when **Relocate** (moving VMware workloads to **Google Cloud VMware Engine** without hypervisor conversion) is tracked separately from **Rehost** (moving VMs to **Google Compute Engine** via **Migrate to Virtual Machines**), the 6 Rs are often referred to as the **7 Rs**.

![Two-stage Google Cloud decision tree: Stage 1 TIME pre-filter and Stage 2 7 Rs tree with a separate Relocate path.](./images/089b1c22-02d9-4e67-a9f5-413a2a60d13c.png)

The diagram, the editable [draw.io model](./samples/6Rs-DecisionTree-GCP-baseModel.drawio), and the Mermaid flowchart in the [decision tree guide](./6rs-decision-tree.md) follow the same logic: Stage 1 (redundancy check and TIME disposition) runs first, and Stage 2 separates **Relocate** (Google Cloud VMware Engine) from **Rehost** (Compute Engine) through an explicit VMware question.

The first step is to update the business drivers at the top of the tree with those defined by your organization. Next, apply the tree to **application components** rather than applications as a whole. For example, in a three-tier application (front-end, application layer, and database), each component should transit the tree independently and be assigned a specific strategy and Google Cloud target pattern—such as containerizing the stateless web/app tiers onto **Cloud Run** or **GKE Autopilot** (**Replatform**) while moving the database tier to **Cloud SQL** or **AlloyDB** (**Replatform**) or **Compute Engine** (**Rehost**).

### Key Google Cloud workload and licensing checks in the decision tree

When evaluating the decision nodes **"All licenses and products supported in Google Cloud?"** and **"Is upgrade supported or move to Google Cloud managed service possible?"** (and choosing between **Rehost** and **Relocate**), apply these Google Cloud-specific rules (detailed further in [6rs-decision-tree.md](./6rs-decision-tree.md)):

- **VMware estate (Rehost vs. Relocate):** Choose **Relocate $\rightarrow$ Google Cloud VMware Engine (GCVE)** via VMware HCX when you need the fastest possible data-center exit without changing guest OS images, IP addresses, or vSphere/NSX operational tooling. Choose **Rehost $\rightarrow$ Google Compute Engine (GCE)** via **Migrate to Virtual Machines (M2VM)** when you want to exit VMware licensing costs and right-size onto native GCE Custom Machine Types with Committed Use Discounts (CUDs).
- **Oracle databases:** Standard shared-tenancy public cloud vCPUs require careful review of Oracle licensing terms. Choose between **[Oracle Database@Google Cloud](https://cloud.google.com/oracle/database/docs/overview)** (OCI Exadata / Autonomous Database running inside Google Cloud data centers with BYOL/ULA support), **[Bare Metal Solution (BMS) for Oracle](https://cloud.google.com/bare-metal)** (dedicated physical socket/core servers for strict BYOL compliance), or **Replatform / Modernize $\rightarrow$ AlloyDB for PostgreSQL or Cloud SQL** using **[Database Migration Assessment (DMA)](https://github.com/GoogleCloudPlatform/database-assessment)** and **DMS Conversion Workspaces**.
- **Microsoft Windows Server & SQL Server:** Choose between **License-Included (PAYG)** images on Compute Engine / **Cloud SQL for SQL Server**; **BYOL on multi-tenant Compute Engine** for SQL Server and other eligible Microsoft *server applications* with active Software Assurance and License Mobility; **BYOL on Compute Engine sole-tenant nodes** for Windows Server (Windows Server is not covered by License Mobility); or modernizing .NET and SQL Server onto **Linux containers (GKE / Cloud Run) + AlloyDB**. **Caveat:** Microsoft's October 1, 2019 licensing change limits bring-your-own Windows Server licenses on dedicated hosts at listed cloud providers, including Google Cloud. Generally, only product versions released before that date (for example, Windows Server 2019 or earlier — not Windows Server 2022 or later) and licenses acquired under an enrollment effective before that date (or trued-up under such an Enterprise Agreement) qualify. Validate eligibility with the [Microsoft licensing FAQ for Compute Engine](https://cloud.google.com/compute/docs/instances/windows/ms-licensing-faq) and your Microsoft licensing specialist; otherwise use license-included images.
- **SAP workloads:** Run SAP HANA on SAP-certified memory-optimized Compute Engine series (such as `M2`, `M3`, and `X4`, which scales up to 32 TB of memory) or on Bare Metal Solution, and run SAP NetWeaver / S/4HANA application servers on certified general-purpose series (such as `C3` and `N2`). Always confirm the exact machine type against the [SAP HANA certifications list](https://cloud.google.com/sap/docs/certifications-sap-hana).
- **Mainframe & legacy Unix (AIX / Solaris / HP-UX):** Use **[Google Cloud Mainframe Modernization](https://cloud.google.com/mainframe-modernization)** (Mainframe Assessment Tool + Dual Run) to replatform or automated-refactor mainframe workloads to **GKE / Cloud Run + Cloud SQL / AlloyDB**. For RISC/Unix systems (AIX, Solaris, HP-UX), branch to **Replatform** (re-compile/port to Linux on GCE/GKE and migrate databases via DMS), **Repurchase (SaaS)**, or **Retain**.

Before using the decision tree across the full portfolio, test the logic with a few sample applications and confirm that you agree with the outcome. Treat edge cases as documented exceptions rather than proliferating multiple versions of the tree. General guidance is that the base tree should accurately classify at least 70–80 percent of workloads. Further iterations and refinement occur in [portfolio analysis and migration planning](./04-portfolio-analysis-migration-planning.md).
