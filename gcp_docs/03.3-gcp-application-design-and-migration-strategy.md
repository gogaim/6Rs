# Google Cloud application design and migration strategy

Designing and documenting the future state of your application is a key migration success factor. We recommend creating a design for any type of migration strategy, no matter how simple or complex. Creating the design will surface potential blockers, dependencies, and opportunities to optimize the application even in cases where the architecture is not expected to change. In addition, the resulting design will serve as a base for further evolution after the migration.

Besides the importance of the design process, it can also become a blocker and impact migration speed. This happens because of legacy architectural review processes that were conceived for on-premises systems. We recommend that you review your architectural review and approval process and focus on establishing architectural patterns or archetypes that can be preapproved. Do not underestimate the effort of reviewing architectures for hundreds or thousands of applications, and take the opportunity to modernize the process.

The following list contains Google Cloud resources to aid the design process:

- [Google Cloud Architecture Center](https://cloud.google.com/architecture) combines tools, reference architectures, and guidance, including the [Google Cloud Well-Architected Framework](https://cloud.google.com/architecture/framework).
- [Google SRE Books & Workbook](https://sre.google/books/) contains resources about how Google builds, scales, and operates reliable software systems.
- [Google Cloud Solutions & Jump Start Solutions](https://cloud.google.com/solutions) offers pre-built deployment blueprints and reference architectures for common technical and business workloads.
- [Migration to Google Cloud Guidance](https://cloud.google.com/architecture/migration-to-gcp-getting-started) provides strategies, guides, and patterns that aid the design process and migration best practices.
- [Google Cloud Documentation](https://cloud.google.com/docs) contains comprehensive documentation for all Google Cloud services, including guides and API references.
- [Google Cloud Skills Boost & Getting Started](https://cloud.google.com/docs/get-started) provides hands-on tutorials and labs to learn the fundamentals of building in Google Cloud.

Depending on where you are in the cloud journey, Google Cloud foundations might already exist. These Google Cloud foundations include the following:

- Target Google Cloud regions and zones have been identified.
- Resource hierarchy (Organization, Folders, and Projects) and Billing Accounts have been created or can be provisioned on demand via Terraform.
- Shared VPC and hybrid networking (Cloud Interconnect / Cloud VPN) have been implemented.
- Foundational security, logging, and operations services have been deployed across the organization.

Conversely, you might be early in the process, and Google Cloud foundations are not yet established. A lack of established foundations could limit the scope of your application design or require further work to define them. If this is the case, we recommend defining and implementing the foundational design of the landing zone in parallel with the application design work. The application design helps to identify requirements such as Google Cloud folder and project structure, Shared VPC networking, subnet CIDR ranges, shared services, security controls, and cloud operations.

The [Google Cloud Enterprise Foundations Blueprint](https://cloud.google.com/architecture/security-foundations) and [Cloud Foundation Toolkit (CFT)](https://cloud.google.com/foundation-toolkit) provide an opinionated, Terraform-automated way to set up and govern a secure, multi-project Google Cloud landing zone using Resource Manager, Cloud IAM, Organization Policy constraints, and Security Command Center.

## Application future state

Start by establishing the initial migration strategy for this application. At this point, the strategy is considered initial because it could change as part of the future state design, which can uncover potential limitations. To validate initial assumptions, see the [6 Rs decision tree](./02.4-prioritization-and-migration-strategy.md) and [6 Rs Decision Tree Guide](./6rs-decision-tree.md). Also, document potential migration phases. For example, will this application be migrated in a single event (all components are migrated at the same time)? Or is this a phased migration (some components are migrated later)?

Note that migration strategies for a given application might not be unique. This is because multiple R types could be used to migrate the application components. For example, the initial approach could be to lift and shift the application without changes. However, an application's components might reside in different infrastructure assets that might require diverse treatments. For example, an application is made up of three components, each running on a separate server, and one of the servers runs a legacy operating system that isn't supported in the cloud. That component will require a replatform approach, while the other two components, running in supported server versions, can be rehosted. It is key to assign a migration strategy to each application component and associated infrastructure that is being migrated.

Next, document the context and problem, and link existing artifacts that define the current state:

- Why is this application being migrated or modernized?
- What are the proposed changes?
- What are the benefits?
- Are there any major risks or blockers?
- What are the current downsides?
- What is in scope and out of scope?

## Repeatability

Throughout the design work, consider how this solution and architecture for this application can be reused for other applications. Can this solution be generalized into a reusable archetype?

## Requirements

Document the functional and nonfunctional requirements for this application, including security. This includes current and future state requirements, depending on the migration strategy chosen. Use the information gathered during the detailed application assessment to guide this process.

## To-be architecture

Describe the future architecture for this application. Consider creating a reusable diagram template (for example, using the official [Google Cloud architecture icons](https://cloud.google.com/icons) in your preferred diagramming tool) that contains building blocks for your source environment (on-premises) and target Google Cloud environment (for example, target Google Cloud region, Host/Service projects, Shared VPC, and zones).

Create a table of components that are being migrated and components that will be new. Include other applications and services (either on premises or in the cloud) that interact with this application.

The following table lists example components mapped to Google Cloud services. It does not represent a reference architecture or vetted configuration.

| Name | Description | Google Cloud Target Details |

After the components have been identified, plot them in a diagram using your preferred tool. Share the initial design with the key application stakeholders, including application owners, enterprise architects, and the platform and migration teams. Consider asking the following questions:

- Does the team generally agree with the design?
- Can the operations teams support it?
- Can the design be evolved?
- Are there other options?
- Does the design comply with architectural standards and Organization Policy security constraints?
- Are any components missing (for example, Artifact Registry, Cloud Build / CI/CD pipelines, Private Service Connect endpoints)?

## Architectural decisions

As part of the design process, you will likely find more options for the overall architecture or specific parts of it. Document these options alongside the rationale for a preferred or selected option as Architecture Decision Records (ADRs).

Ensure that the main options are listed and described with enough detail for a new reader to understand the options and reasons behind a decision to use one option over another.

## Software lifecycle environments

Document any changes to current environments. For example, test and development environments will be provisioned as separate Google Cloud projects (e.g., `app-dev`, `app-staging`, `app-prod`) using Terraform and not migrated via lift-and-shift.

## Labels and tags

Describe mandatory and recommended [Google Cloud labels](https://cloud.google.com/compute/docs/labeling-resources) (for cost allocation/billing export, environment, owner, application ID, and cost center) and [Network/IAM Tags](https://cloud.google.com/resource-manager/docs/tags/tags-overview) for each infrastructure component in the design.

## Migration strategy

By this point of the design, the initial assumptions about migration strategy should be validated. Confirm that there is consensus on the chosen R strategy. Document the overall application migration strategy and the strategies for individual application components. As mentioned previously, different application components might require different R types for migration.

In addition, align the migration strategy to key business drivers and outcomes. Also, describe any phased approach to migration, such as the movement of components in different migration events.

For more information about determining your 6 Rs and modernization fit on Google Cloud, see [Google Cloud Migration Center recommendations](https://cloud.google.com/migration-center/docs/migration-preferences).

## Migration patterns and tools

With a defined migration strategy for the application and infrastructure components, you can now explore specific technical patterns:

- **Rehost (Lift and Shift):** Implement using [Google Cloud Migrate to Virtual Machines (M2VM)](https://cloud.google.com/migrate/virtual-machines) for agentless replication from VMware vSphere, AWS, or Azure into **Compute Engine**. If you don't need to replicate state or disk data, you can achieve the same outcome by baking a **Compute Engine Custom Image** with Packer/Cloud Build and deploying via Terraform and Managed Instance Groups (MIGs).
- **Relocate (VMware):** Move VMware workloads rapidly without hypervisor conversion to [Google Cloud VMware Engine (GCVE)](https://cloud.google.com/vmware-engine) using VMware HCX.
- **Replatform / Refactor (Containers & Databases):**
  - **Containerization:** Use [Migrate to Containers (M2C)](https://cloud.google.com/migrate/containers) to extract and containerize Linux/Windows workloads directly into [Google Kubernetes Engine (GKE Standard or GKE Autopilot)](https://cloud.google.com/kubernetes-engine) or [Cloud Run](https://cloud.google.com/run).
  - **Database Modernization:** Use the open-source [Database Migration Assessment (DMA)](https://github.com/GoogleCloudPlatform/database-assessment) and [Google Cloud Database Migration Service (DMS)](https://cloud.google.com/database-migration) (with Gemini-assisted Conversion Workspaces) to migrate homogeneous or heterogeneous databases (such as Oracle or SQL Server) to **Cloud SQL** or **AlloyDB for PostgreSQL**.
  - **Data Transfer:** Use [Storage Transfer Service](https://cloud.google.com/storage-transfer-service) for online file/object transfers or [Transfer Appliance](https://cloud.google.com/transfer-appliance) for offline petabyte-scale data movement.
- **Repurchase:** Deploy commercial off-the-shelf (COTS) VM/Kubernetes solutions or subscribe to SaaS offerings directly through [Google Cloud Marketplace](https://cloud.google.com/marketplace) (leveraging existing Google Cloud commit spend).

Evaluate the different patterns and options that are available for achieving the goal. Consider pros and cons, and migration operational readiness. To help with your analysis, use the following questions:

- Can migration teams support these patterns?
- What is the balance between cost and benefits?
- Can this application, service, or component be moved to a Google Cloud managed service (such as Cloud Run, GKE Autopilot, Cloud SQL, or AlloyDB)?
- What is the effort to implement this pattern?
- Is there any regulation or compliance policy (for example, data residency / Assured Workloads) preventing the use of a specific pattern?
- Can this pattern be reused? Reusable patterns are preferred. However, sometimes a pattern will be used only one time. Consider balance between the effort of a single-use pattern over an alternative reusable pattern.

## Service management and operations

When creating application designs for migration to Google Cloud, consider operational readiness. When evaluating readiness requirements with your application and infrastructure teams, consider the following questions:

- Are they ready to operate it using Google Cloud Observability, Cloud IAM, and Terraform?
- Are incident response procedures defined?
- What is the expected service level agreement (SLA) and Service Level Objective (SLO)?
- Is separation of duty required across Google Cloud projects and IAM roles?
- Are the different teams ready to coordinate support actions?
- Who is responsible for what?

## Cutover considerations

Considering the migration strategy and patterns, what is important to know at the moment the application is migrated? Cutover planning is a post-design activity. However, document any considerations for activities and requirements that can be anticipated. For example, document the requirement to perform a proof of concept or test-clone cutover in Migrate to Virtual Machines, if applicable, and outline the test, audit, or validation requirements.

## Risks, assumptions, issues, and dependencies

Document any open risks, assumptions, and potential issues that are not yet resolved. Assign clear ownership to these items, and track progress so that the overall design and strategy can be approved for implementation. In addition, document key dependencies for implementing this design.

## Estimating run cost

To estimate the cost of your target Google Cloud architecture, use the [Google Cloud Pricing Calculator](https://cloud.google.com/products/calculator) or export a TCO report from [Google Cloud Migration Center](https://cloud.google.com/migration-center). Add your infrastructure components as defined by your design—modeling **1-year or 3-year Committed Use Discounts (CUDs)** for steady-state workloads (`>63%` or `>45%` utilization, billed monthly with zero upfront payment) or automatic **Sustained Use Discounts (SUDs)** on eligible on-demand machine series (`N1`, `N2`, `N2D`, `C2`, `M1`, `M2`; note that CUDs and SUDs do not stack on the same usage)—and obtain an estimated run cost. Factor in third-party software licenses (such as BYOL on Sole-Tenant Nodes or Bare Metal Solution vs. license-included Windows Server, RHEL, SUSE, or SQL Server images on Compute Engine) that are required for your application components.
